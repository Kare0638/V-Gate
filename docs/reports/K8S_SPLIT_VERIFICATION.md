Deploys the gateway/worker split on a local kind cluster, serves a
request end to end, removes a worker while traffic is flowing, and
brings it back.

## What to read in the log below

- **Step 6** — the `NODE` column. The two workers must land on
  different nodes, or the per-pod routing below never crosses a
  network boundary and proves less than it appears to. The two
  bound PVCs are the same point for storage: a single
  `ReadWriteOnce` claim could not serve pods on two nodes.
- **Step 7** — the two DNS answers must be *different* addresses.
  One shared address would leave the gateway unable to tell
  workers apart, and is what a load-balanced Service IP gives.
- **Step 10** — request counts should be split across both
  workers. This is round-robin; it is not load-aware.
- **Step 11** — the status-code histogram is the real result.
  Requests keep flowing while a worker is removed, so this counts
  what the removal cost. All `200` is common but not guaranteed:
  read the outcome metrics printed underneath before concluding
  anything from a non-200. A `connect_error` was never delivered
  and gets retried on another worker; a `request_error` was
  already in flight when the pod died and is deliberately not
  retried, because the worker may already be generating and one
  client request must not cost two generations. The second class
  reaching the client as a 500 is the policy working, not a bug.
  Removing that window needs draining — see ROADMAP.md.
- **Step 12** — the point of DNS discovery. `kubectl scale` is
  run against the StatefulSet and the gateway is expected to pick
  the change up on its own. With the static endpoint list this
  replaced, a new pod received no traffic and a removed one was
  probed forever, and the only fix was editing the gateway's
  manifest. Endpoints must also read as `vgate-worker-<n>.`
  rather than as addresses: a restarted pod returns on a new IP,
  and every `vgate_worker_*` metric is labelled by endpoint, so
  address identity would add a time series per restart. The run
  also scales to zero and back, which is the boundary an earlier
  version skipped by going 1 -> 3 -> 2: an empty resolve is
  ambiguous, and the first guard against DNS blips ignored empty
  answers unconditionally, keeping the last worker in the
  registry forever.
- **Step 13** — `state_changes_total` separates three things.
  `admitted` is a discovered worker entering rotation for the
  first time, after a probe proved it usable; discovered arrivals
  start out of rotation, because the worker Service publishes
  not-ready addresses on purpose and a pod still loading weights
  is therefore in the DNS answer. `removed` here is normal
  during pod termination: a terminating pod stays in DNS while it
  stops answering, so probes fail before discovery drops it.
  `recovered` is a worker that was demoted and came back while
  still a member. A gateway holding zero workers still passes its
  own readiness probe — see ROADMAP.md; that gap is unchanged.
