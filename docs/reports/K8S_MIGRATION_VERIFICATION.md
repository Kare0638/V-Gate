## What to read in the log below

- **Phase 2, endpoint list** — after the plain apply, `Service/vgate`
  should list *both* the old monolith pod and the new gateway pod.
  The old pods carry `app.kubernetes.io/component=gateway`, which is
  exactly what the new Service selects on, so nothing removes them.
- **Phase 2, response tally** — traffic sent through the Service from
  inside the cluster, so kube-proxy load balances it. Responses
  split between the two processes. The old monolith still validates
  the API key from the ConfigMap it mounted at start, not the one
  the new Secret supplies, so its share comes back `401`; a
  `200` whose /stats has no `workers` key is the monolith
  answering an inference path that does no worker routing at all.
- **Phase 3** — the same tally after migrating. Every response
  should come from the new gateway, and no pre-split object should
  remain.
